# 0002 — Додати Redis як спільну інфраструктуру для обмеження запитів і кешу peer-blob

- **Status:** Accepted
- **Date:** 2026-05-23
- **Deciders:** genkovich (Architect), Tech Lead (sign-off)

## Контекст

PRD `course-lesson-mvp` ставить дві вимоги, які наявний стек не покриває:

1. **Обмеження запитів** (англ. *rate-limit*). PRD §6.1 abuse-case #4 — не більше 30 запитів за хвилину з одного користувача на `POST /courses`. PRD §6.1 abuse-case #8 — не більше 10 коментарів за годину з одного користувача на `POST /lessons/{id}/comments`.
2. **Швидкий перегляд уроку з даними сусідів.** PRD §6 NFR — `GET /lessons/{id}` має повертати урок разом з peer-blob (агрегованими даними про те, скільки сусідів зі студентом-читачем вже завершили цей урок) за `≤ 400 мс p95` (тобто у 95% запитів швидше за 400 мс). Цей агрегований запит сам по собі занадто повільний — потрібен **кеш з коротким життям** (60 секунд).

Поточний BeerLMS-репозиторій **не має Redis** у стеку — є тільки Postgres + бібліотека `pgx`. Перевірка репозиторію (Explore-сканування) це підтверджує. Тобто це **фундаментальне рішення про інфраструктуру** — додати новий компонент vs. знайти обхідний шлях.

Це рішення впливає на §4 (стратегія обмеження запитів), §5 (вид контейнерів), §7 (моніторинг розгортання), §8 (наскрізна конвенція кешу) у sad.md.

## Драйвери рішення

- **PRD §6.1 abuse case #4:** ліміт 30 запитів/хв на `POST /courses` має бути **per-user**, не per-instance.
- **PRD §6.1 abuse case #8:** ліміт 10 коментарів/год на `POST /comments` — теж per-user.
- **PRD §6 NFR:** `GET /lessons/{id}` з peer-blob ≤ 400 мс p95 під високим навантаженням.
- **SAD §1 QG-3 (доступність):** під час збою кешу — система не повинна падати. Має бути запасний шлях: читати з БД напряму (повільніше, але працює). PRD §6 NFR прямо згадує цей запасний шлях.
- **Constraint:** у поточному стеку немає Redis (з Explore §d). Введення нової інфраструктури — це рішення про DevOps-витрати.

## Розглянуті варіанти

1. **Додати Redis як спільну інфраструктуру.** Розгорнути Redis у production; використати його для (а) лічильника запитів на користувача — спільного між API-репліками; (б) кешу peer-blob з 60-секундним терміном життя (`SET key EX 60`).
2. **Тільки Postgres (advisory locks + попередньо порахована таблиця).** Лічильник запитів — окрема таблиця у Postgres з advisory-локами (Postgres-механізм для координації паралельних операцій). Peer-blob — попередньо порахована таблиця (англ. *materialized view* — таблиця, яка зберігає результат SELECT і оновлюється раз на N секунд через cron-завдання), яку оновлює pg_cron кожні 60 с.
3. **In-process per-instance (без спільної інфраструктури).** Лічильник запитів — у памʼяті процесу Go (`golang.org/x/time/rate`). Peer-blob — кеш у памʼяті процесу (LRU per replica — кожна репліка тримає власний кеш).

## Результат рішення

**Обрано:** Варіант 1 — Додати Redis як спільну інфраструктуру.

**Чому переміг:**

- PRD вимагає **per-user** ліміт, не per-instance. Варіант 3 (in-process) технічно ламає цю специфікацію: якщо у нас 3 API-репліки, користувач може зробити по 30 запитів через кожну з них = 90 запитів/хв. Спільний лічильник між репліками — це або зовнішнє сховище (Redis), або складна координація.
- Варіант 2 (тільки Postgres) додає тиск на пул зʼєднань через лічильник запитів на гарячому шляху. Запит до Redis займає <5 мс; запит до попередньо порахованої таблиці на холодному кеші — 200-300 мс. Це ламає `QG-3` (немає окремого шару кешу, який можна «вбити» у chaos-drill — навіть тренування на збій неможливе).
- Модуль mentorship у наступному кварталі планує **кеш токенів сесії + відстеження присутності**. Redis як спільна інфраструктура **амортизується між модулями** — DevOps-витрати робиш один раз, користуються кілька функцій.
- Семантика лічильника запитів простіша у Redis: команда `INCR` + час життя у одній операції. У Postgres це складна SQL-логіка з блокуваннями.

## Наслідки

**Позитивні:**

- PRD §6 NFR на обмеження запитів і швидкість peer-blob виконуються напряму, без компромісу.
- Майбутні модулі (mentorship — токени сесії, присутність) реюзають той самий Redis — амортизація DevOps-витрат.
- SAD §1 QG-3 chaos-drill «вбий Redis-pod → запасний шлях на читання з БД» — можна перевірити, бо є окремий шар, який можна «вбити».
- Семантика лічильника запитів чиста (`INCR` + час життя), проти складних SQL-лічильників.

**Негативні:**

- **DevOps-витрати на введення:** новий компонент у production потребує деплою / моніторингу / резервного копіювання / високої доступності — це не безкоштовно.
- **Складність pipeline розгортання:** dev-середовище (Docker-compose) має включати Redis-сервіс; інтеграційні тести у CI мають `redis://localhost:6379`.
- **Введення Redis у production — незворотнє рішення без значного rework.** Якщо у v2 захочемо прибрати — треба переписати: (а) обмеження запитів на in-process per-instance (з втратою справедливості при кількох інстансах) або на Postgres advisory locks; (б) кеш peer-blob на попередньо порахавану таблицю або per-instance LRU.

**Нейтральні:**

- Міграція на elasticache / managed Redis (AWS / GCP) у v2 — можлива. Інтерфейс на рівні застосунку не змінюється.
- Версія Redis: ≥ 7 (для `OBJECT FREQ` policy + I/O threading); рекомендовано Redis 7.2.
