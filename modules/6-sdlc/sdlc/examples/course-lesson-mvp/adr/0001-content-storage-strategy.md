# 0001 — Зберігати урок як таблицю блоків різних типів

- **Status:** Accepted
- **Date:** 2026-05-23
- **Deciders:** genkovich (Architect), Tech Lead (sign-off)

## Контекст

PRD §4 говорить: methodist складає урок зі змішаного контенту — текст + вбудоване відео + картинки + блоки коду — і натискає **Опублікувати**. Учень потім читає той самий урок у браузері, а методист хоче на льоту переставляти, видаляти, додавати блоки під час редагування.

Питання, на яке відповідає цей ADR: **у якій формі ми зберігаємо тіло уроку у БД?** Це фундаментальне рішення — від нього залежить, як виглядатиме API (`GET /lessons/{id}` повертає масив блоків чи цілісний JSON-blob?), як працює фронт (редактор збирає блоки чи цілісний документ?), як виконується перевпорядкування при редагуванні, і чи можна шукати всередині уроку.

Згідно евристики *масштабу удару* (blast radius — наскільки боляче буде передумати): рішення **незворотнє** (через 3 місяці методисти наповнять десятки уроків, переробка = міграція даних з простоєм), **торкається кількох модулів** (фронт-редактор ↔ бек-API ↔ медіа-обробник), і **має справжні альтернативи** (цілісний JSON у файловому сховищі — не straw-man). Усі три критерії дають PASS → це ADR-рівне рішення.

## Драйвери рішення

- **PRD §6 NFR:** збереження редагування блоку — `≤500 мс p95` (*p95* — у 95% запитів швидше, 5% повільніше); рендер сторінки учня — `≤1 с p95`.
- **PRD §4 user story:** методист має змогу переставити блоки місцями всередині уроку без перезавантаження сторінки.
- **§4 SAD стратегія:** структурований стан у БД (а не «один цілісний документ десь»), щоб API віддавав готову форму, а фронт малював.
- **Існуюча інфраструктура:** Postgres уже в стеку. S3 уже використовується для медіа-файлів (відео, картинки). Нової інфраструктури не вводимо.
- **Обмеження:** немає Mongo/документної БД у репо — рішення «JSONB-колонка» все одно живе у Postgres, не у новій БД.

## Розглянуті варіанти

1. **Таблиця блоків різних типів + окрема таблиця медіа.** Дві нові таблиці: `lesson_blocks (id, lesson_id, sequence INT, type, content)` і `media_blobs (id, s3_url, mime, …)`. Колонка `sequence` зберігає порядок. Бек віддає JSON-масив блоків з посиланнями на медіа.
2. **Один цілісний JSON-обʼєкт у S3, метадані у БД.** Фронт-редактор серіалізує цілий урок у JSON, кладе у S3 як `lessons/{id}.json`, у БД зберігається тільки `lesson_id → s3_key + updated_at`. API при читанні віддає підписане посилання або проксує контент.
3. **Дві окремі сутності `text_blocks` + `media_blocks`, JOIN на API-рівні.** Чисте розділення за типом контенту. API при `GET /lessons/{id}` робить два запити і зливає результат за `sequence`.

## Результат рішення

**Обрано:** Варіант 1 — таблиця блоків різних типів + окрема таблиця медіа.

**Чому переміг:**

- **NFR p95 ≤500 мс на редагування виконується природно** — `UPDATE lesson_blocks SET content=$1 WHERE id=$2` зачіпає один рядок, без перезавантаження цілого документа (як вимагав би варіант 2).
- **Перевпорядкування блоків — одна транзакція з кількома UPDATE на `sequence`**, без переписування всього файлу у S3. Варіант 2 при перетягуванні одного блоку змушує фронт відправити цілий урок ≈100 КБ.
- **API віддає готову структуру** — фронт малює блоки без додаткового парсингу JSON-документа. Варіант 3 ламає принцип «mixed content», бо `text_blocks` і `media_blocks` живуть як дві окремі абстракції, які доводиться зшивати у клієнті.
- **Postgres-only підхід узгоджується з §4 стратегією** — ми не вводимо нову файлову модель для контенту (S3 залишається тільки для **медіа-файлів**, не для тіла уроку).

## Наслідки

**Позитивні:**

- Атомарні редагування на рівні блоку — `UPDATE` один рядок, NFR виконується.
- Перевпорядкування — одна транзакція на 2-5 `UPDATE` блоків (sequence column).
- Структурований повнотекстовий пошук всередині уроку можливий через звичайний `LIKE` або `tsvector` по `content` колонці — без додаткових індексів типу GIN.
- Додавання нового типу блоку у v1.1 (наприклад, опитування) — нова `type='poll'`, без зміни схеми таблиці.

**Негативні:**

- Дві нові таблиці у міграції: `lesson_blocks` + `media_blobs`. Це більше схеми, ніж варіант 2 (`lessons` + S3-ключ).
- Збереження порядку блоків через колонку `sequence INT` потребує окремого UNIQUE-обмеження `(lesson_id, sequence)` — це окрема архітектурна деталь, винесена у **ADR-сусід** про перевпорядкування на рівні БД (буде створено у наступному проході).
- При вставці блоку посередині (drag-and-drop у редакторі) — треба UPDATE-ити `sequence` у всіх блоків після нього. Це **N UPDATE на одне переставлення**, де N — кількість блоків після точки вставки. Прийнятно для уроків ≤30 блоків (типовий розмір — 10-15).

**Нейтральні:**

- Міграція на варіант 2 (цілісний JSON у S3) у v2 теоретично можлива — пишемо скрипт «прочитай таблицю блоків → серіалізуй у JSON → поклади у S3», але це тижні роботи з простоєм. **Тому це і ADR**: вибір змінити пізніше — дорого.
- Версія Postgres: ≥15 (вже зафіксовано у §2 SAD).
