# 11.3-audit-config · фікстура для аудиту «MCP чи CLI»

Готовий `.mcp.json` з чотирма типовими серверами - для лекції 11.3. Якщо у тебе ще нема власного набору підключених
серверів - скопіюй цей файл у тестовий проєкт і працюй з ним.

## Що всередині

| Сервер | Транспорт | Що дає агенту |
|---|---|---|
| `github` | remote HTTP | PR, issues, workflows твоїх репозиторіїв |
| `context7` | remote HTTP | актуальна документація бібліотек у контекст |
| `playwright` | stdio (npx) | живий браузер: навігація, кліки, скріншоти |
| `filesystem` | stdio (npx, запінена версія) | читання/запис файлів у вказаній теці |

## Завдання аудиту

По кожному серверу пройди три питання з лекції 11.3:

1. Яку частку моїх задач цей сервер закриває і як часто я його смикаю?
2. Чи існує зрілий CLI-інструмент під той самий сервіс, синтаксис якого модель
   знає з тренування?
3. Що я плачу за MCP-варіант: скільки tool definitions їде у кожен запит сесії?
   (Підказка: `/context` показує, скільки токенів з'їдають підключені сервери.)

Один сервер із чотирьох заміни на CLI-альтернативу і прожени через неї ту саму
задачу. Порівняй токени, надійність і зручність - і прийми рішення: повертати
сервер чи лишити CLI. Доказ для домашки - 3-5 речень порівняння.

Деталь для уважних: версія `filesystem` запінена (`@2026.1.14`), а `playwright`
їде на `@latest`. Це теж матеріал для аудиту - який із двох підходів безпечніший
для команди і чому (лекція 8.10 про supply chain підкаже).
