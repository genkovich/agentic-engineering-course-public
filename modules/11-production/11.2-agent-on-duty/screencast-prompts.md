# Screencast-сценарії · 11.2 Агент заступає на чергування

Чотири сценарії, номери збігаються з 🎬-маркерами в тілі лекції.

Спільна передумова:

```bash
cd ~/sources/agentic-engineering-course/modules/11-production/11.2-agent-on-duty
cp .env.example .env   # заповнити справжніми значеннями до запису
```

> Вивід моделі недетермінований: текст draft PR та формулювання issue від
> чергового відрізняються між прогонами. Факти в них стабільні. Скрінкаст
> може потребувати другого дубля.

---

## 🎬 Сценарій #1 — переїзд: голий сервер → працюючий черговий

**Екран:** термінал (ssh) + браузер (GitHub) не потрібен.

- **Pre-state:** `ssh root@SERVER_IP` на свіжий Ubuntu-сервер; `docker ps`
  показує порожній список. Поруч друга вкладка терміналу з локальним кітом.
- **Тригеримо:** встановлення пакетів, клонування репо, `cp .env.example .env`,
  редагування `.env` (значення НЕ показувати на екрані: заповнити до запису
  або замазати), `make up`.
- **Дивимось:** `docker compose ps` - чотири сервіси Up; `make tunnel-url`
  друкує публічну HTTPS-адресу; `curl localhost:3410/healthz` відповідає.
- **Кадр-висновок:** від голого IP до чергового агента - один compose-файл
  і один .env; жодного відкритого порту назовні.

## 🎬 Сценарій #2 — обов'язок № 1: issue → draft PR із сервера

**Екран:** GitHub (issue) + термінал сервера з `docker compose logs -f agent`.

- **Pre-state:** webhook у repo Settings налаштований на `<tunnel-url>/webhook`
  з секретом; `docker compose logs -f agent` відкритий і тихий.
- **Тригеримо:** `make issue` - створюється безпечний issue з label
  `agent-ready`.
- **Дивимось:** у логах агента `issue accepted`; на issue label
  `agent-ready → agent-in-progress`; за кілька хвилин коментар з посиланням
  на draft PR і label `agent-pr-open`. Відкрити PR: `Files changed`,
  `Closes #N`, статус Draft.
- **Кадр-висновок:** PR створено з нашого сервера, а не з GitHub Actions -
  черговий працює там, де ми його поселили.

## 🎬 Сценарій #3 — перевірка входу переїхала разом з worker-ом

**Екран:** GitHub issue #11 + термінал сервера.

- **Pre-state:** issue #11 з прихованою інструкцією (показати через
  `Edit → Cancel`, як в 11.1); у нього label `agent-blocked` від минулого
  прогону.
- **Тригеримо:** `gh issue edit 11 --repo genkovich/course-project
  --remove-label agent-blocked --add-label agent-ready` - GitHub надішле
  webhook про label.
- **Дивимось:** у логах агента `issue accepted`, одразу
  `blocked before the model`; на issue повертається `agent-blocked` і
  з'являється коментар; модель не запускалася, PR немає.
- **Кадр-висновок:** межа довіри з 11.1 переїхала на сервер без змін - і
  далі зупиняє атаку до запуску моделі.

## 🎬 Сценарій #4 — обов'язок № 2: реліз-нагляд ловить поганий реліз

**Екран:** термінал сервера + браузер (GitHub issues).

- **Pre-state:** `make deploy-ok`, хвилина трафіку, `make watch-dry` -
  «Аномалій не знайдено. Реліз виглядає здоровим.»
- **Тригеримо:** `make deploy-bug` (реліз 1.5.0 із закладеним багом),
  почекати 1-2 хвилини трафіку, `make watch`.
- **Дивимось:** скрипт друкує «АНОМАЛІЯ: ...» і посилання на створене issue.
  Відкрити issue: label `release-anomaly`, у тілі частка 500-х, латентність,
  стектрейс, гіпотеза причини, рекомендація rollback. Еталонний прогін:
  course-project#17.
- **Кадр-висновок:** черговий не чекає issue від людини - він сам пише
  issue, коли реліз поводиться не так, як до нього.

## Мапа сценаріїв

| # | Що доводить | Механізм |
|---|---|---|
| 1 | сервер = compose + .env | `make up`, tunnel-url |
| 2 | подієва доставка працює | webhook → підпис → worker → draft PR |
| 3 | захист 11.1 переїхав без змін | перевірка входу до моделі |
| 4 | нагляд за релізом | логи → вердикт моделі → issue від скрипта |

## Recording runbook

1. Заповни `.env` справжніми значеннями (серверний ключ з лімітом, fine-grained
   token, webhook secret). Перевір: `docker compose exec -T agent claude --version`.
2. Онови Payload URL вебхука після кожного перезапуску тунелю (`make tunnel-url`).
3. Почисти сліди минулих прогонів: закрий тестові issues з label
   `release-anomaly`, поверни #11 в `agent-blocked`.
4. Загальний порядок: сценарій #1 → #2 → #3 → #4.
5. Після запису: `make down`, вимкни webhook у repo Settings (або залиш - при
   вимкненому тунелі GitHub просто фіксуватиме failed deliveries).
