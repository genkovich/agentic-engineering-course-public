# story-28 · Черга в review-order

Реалізувати `sortQueue` у `src/lib/queue.ts` так, щоб чергу можна було показувати в
порядку повторення: спершу те, що ще не оцінювали, далі — те, що дали найнижчу оцінку
(бо саме воно найбільше потребує повторення).

Канал зворотного зв'язку — **детермінований гейт**: на функцію вже написано модульні тести
(`src/lib/queue-sort.test.ts`), і вони ЧЕРВОНІ, бо `sortQueue` поки стаб. Гейт (pre-commit /
Stop-hook / `/verify-gate`) ганяє `tsc --noEmit` + `vitest run` і **не дасть закомітити, поки
тест червоний**. Повідомлення про падіння — сигнал зворотного зв'язку, за яким локалізуєш і
виправляєш.

## Acceptance criteria (Given / When / Then)

**AC-1 · Review-order**
- **Given** черга з оцінених і неоцінених карток.
- **When** викликаємо `sortQueue(queue)`.
- **Then** спершу йдуть неоцінені (`grade === null`), далі оцінені за `grade` зростанням.

**AC-2 · Стабільність**
- **Given** дві картки з однаковим `grade`.
- **When** сортуємо.
- **Then** їхній відносний порядок збігається з вхідним (стабільне сортування).

**AC-3 · Чистота (без мутації входу)**
- **Given** вхідний масив `queue`.
- **When** викликаємо `sortQueue(queue)`.
- **Then** вхідний масив лишається незмінним (повертається новий масив, як у решти функцій
  модуля). Пастка: `queue.sort(...)` мутує на місці — треба `[...queue].sort(...)`.

## Doneness

- `npm test` зелений (усі три AC у `queue-sort.test.ts` проходять).
- `tsc --noEmit` без помилок.
- Вивід `vitest run` вставлено у відповідь як доказ (evidence-before-assertion), коміт проходить.
