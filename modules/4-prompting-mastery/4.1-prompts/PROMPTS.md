Тека `02-few-shot` (порожня, просто робоча тека для сесії).

```

<examples>

## Промпт 3 - Race condition: перелік кроків і перевірка

Тека `03-race-condition`. Міркування в тегах не просимо: Claude Code думає перед відповіддю сам, а прохання виписати міркування в тексті відповіді модель може відхилити.

```
Знайди і виправ race condition у counter.go: 1000 goroutines викликають
Increment(), а в кінці значення менше за 1000.
Спершу перерахуй усі точки доступу до спільного стану, визнач, де саме
конфлікт, і коротко поясни чому. Потім виправлення.
Публічні методи Counter (Increment і Value) не змінюй: на їхніх
сигнатурах тримається код, який їх викликає.
Перевір через go run -race counter.go і покажи вивід. Готово, коли там
expected: 1000, got: 1000 і жодного DATA RACE.
```

## Промпт 4 - Verification loop

Тека `04-verification`.

```

## Промпт 5 - Дозвіл сказати «не знаю»

Тека `01-refactor`. Функції `refreshToken` у коді немає, і це навмисно: подивіться, чи Claude це помітить.

### 5A. Без дозволу

```
У src/auth/parser.ts після валідації онови токен сесії користувача
через наявну функцію refreshToken.
```

### 5B. З дозволом «не знаю»

```
У src/auth/parser.ts після валідації онови токен сесії користувача
через наявну функцію refreshToken з src/auth/.
Спершу відкрий файли в src/auth/ і знайди її. Якщо функції з потрібною
сигнатурою там немає, скажи про це прямо і нічого не вигадуй: запропонуй
створити нову або вкажи найближчу за призначенням. У такому разі код
не міняй, дочекайся моєї відповіді.
```

Після 5B Claude має сказати, що `refreshToken` у `src/auth/` немає, і нічого не змінити. Актуальні моделі часто помічають відсутню функцію і без дозволу, тож 5A теж може закінчитись питанням. Різниця в тому, що 5B задає таку поведінку явно: спершу знайти, а якщо функції немає, нічого не міняти й чекати вашої відповіді. Після 5A перевірте, чи не з'явився виклик функції, якої не існує: `npx tsc --noEmit` має пройти без помилок.
