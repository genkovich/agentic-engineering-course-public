# Screencast-сценарії · 10.6 Self-Improvement Loop

Чотири скринкасти на одному наскрізному кейсі: скіл `triage`, який ми доводимо
від 14/20 до 19/20 на held-out наборі, і дві навмисні пастки (тиха обрізка
`skill_md[:1500]` і забруднений seed).

**Спільна передумова:**

```bash
make setup
cd sandbox
# опційно, для живих прогонів outer loop: claude   (потрібен ANTHROPIC_API_KEY + gh auth)
```

> Вивід агента недетермінований: живий прогін outer loop може дати трохи інше
> формулювання правила чи lessons-рядка. Для запису без витрат і без
> недетермінізму всі числа відтворює детермінований стенд-ін: `make apply-fix`,
> `make seed-bad`, `make fix-seed`. Скринкасти #1/#3/#4 повністю детерміновані;
> у #2 diff і draft PR можна показати або живим агентом, або через `make apply-fix`.

## 🎬 Сценарій #1 — скіл-тріаж лейблить issue, held-out ловить дірку

**Артефакт під оптимізацією:** `.claude/skills/triage/SKILL.md`
**Сигнал:** `eval/run.py` (held-out 14/20) + людські релейбли в git-історії

- **Pre-state:** `cat .claude/skills/triage/SKILL.md` - наївний скіл, лейбл за ключовими словами; `python3 eval/run.py` друкує `14/20` і список шести питань, помилково названих bug.
- **Тригеримо:**
  > «Через скіл triage познач issue у файлі `issues/incoming/how-do-i-rotate-keys.md`.»
- **Дивимось:** скіл повертає `bug`, бо бачить слово «error» у тексті; held-out звіт уже показував цей клас помилок - шість питань у графі bug; золотий лейбл цього issue - `question`.
- **Кадр-висновок:** inner loop - це просто задача в проді. Артефакт, який лагодитимемо, - `SKILL.md`; сигнал про поломку - held-out бал і правка людини.

(Детермінований дубль без claude: `make inner`.)

---

## 🎬 Сценарій #2 — skill-improver дописує lessons.md, пише diff, відкриває draft PR

**Агент:** `.claude/agents/skill-improver.md` (outer loop, обмежений одним файлом + PR)

- **Pre-state:** `git log --oneline` показує кілька людських релейблів (`relabel: ... bug -> question`); `cat lessons.md` - поки порожній заголовок; `python3 eval/run.py` - `14/20`.
- **Тригеримо:**
  > «Запусти агента skill-improver у режимі одного циклу: прочитай дельти релейблів і held-out провали, сформулюй один урок у lessons.md, впиши відповідне правило в triage/SKILL.md, повтори eval і відкрий draft PR зі звітом до-після.»

  Живий прогін: `claude -p --agent skill-improver 'run one improvement cycle'`
  Детермінований дубль (без токенів): `make apply-fix`
- **Дивимось:** у `lessons.md` з'являється один рядок-урок; `git diff .claude/skills/triage/SKILL.md` показує додане правило `- question | how do i, how to`; повторний `python3 eval/run.py` друкує `19/20`; `gh pr view` показує PR у статусі **draft** зі звітом `14/20 -> 19/20`.
- **Кадр-висновок:** скіл переписав сам себе з eval-фідбеку і поклав зміну в draft PR. Петля замкнулась, але останнє слово лишилось за людиною.

## 🎬 Сценарій #3 — бінарний чек проти суб'єктивного, і тихий баг обрізки

- **Pre-state:** `cat eval/judge.py` - бінарний асерт `predicted == gold`; `cat eval/rubric.md` - суб'єктивний критерій «наскільки лейбл вдалий».
- **Тригеримо, крок 1 (суб'єктивний суддя тією самою моделлю) - LIVE-ONLY / цитата кейсу:** показуємо `rubric.md` як приклад: оцінка «наскільки вдало» від тієї самої моделі росте сама собою, тоді як бінарний `python3 eval/run.py` чесно тримає `14/20`. Число «плато 6 з 10» - із зовнішнього Hermes-кейсу (Sources лекції), не детермінований вихід кіту; показуй живим агентом або цитуй як кейс. Крок 2 нижче - повністю детермінований.
- **Тригеримо, крок 2 (тихий баг обрізки):** спершу `make apply-fix` (правило дописане, чесний бал 19/20). Тоді `python3 eval/run.py --buggy` - у судді зашитий зріз `skill_md[:1500]`, що обрізає скіл до 1500 символів; нове правило стоїть у кінці файлу (символ 1589) і в суддю не потрапляє. Прибираємо зріз - `python3 eval/run.py`.
- **Дивимось:** із `--buggy` бал застряг на `14/20` навіть після правильного правила, бо суддя не бачить кінця скіла; без зрізу - `19/20`.
- **Кадр-висновок:** довіряй бінарному чеку, а не суб'єктивному балу тієї самої моделі. І пильнуй тиху обрізку: один зріз `[:1500]` знеструмлює всю петлю мовчки.

## 🎬 Сценарій #4 — навмисно псуємо seed, петля ідеально оптимізує в хибне

- **Pre-state:** `make seed-bad` псує один клас золотих лейблів у held-out (питання позначені як bug навмисно); `python3 eval/run.py` показує «ідеальні» `20/20` на забрудненому наборі.
- **Тригеримо:** проти забрудненого held-out наївний скіл уже «переможний» (20/20), бо його хибний вихід збігається з хибними лейблами; будь-яке «покращення» лише закріпить помилку. Потім `make fix-seed` виправляє золоті лейбли назад, і повторюємо `python3 eval/run.py`.
- **Дивимось:** проти забрудненого набору бал `20/20`; одна правка seed повертає чесний `14/20`, і видно, що «переможний» скіл насправді помилявся на всіх питаннях.
- **Кадр-висновок:** петля оптимізує рівно те, що міряєш. Отруй мішень - і вона доведе тебе до ідеалу в хибну ціль, точно як ті десять циклів генерації зображень.

## Мапа сценаріїв

| Скринкаст | Що доводить | Детермінований таргет |
|---|---|---|
| #1 | inner loop = задача в проді; артефакт = SKILL.md | `make inner` |
| #2 | outer loop переписує скіл → draft PR | `make apply-fix` (+ живий `claude -p --agent skill-improver`) |
| #3 | бінарний чек > суб'єктивний; баг `skill_md[:1500]` | `make apply-fix` + `python3 eval/run.py --buggy` |
| #4 | хибна ціль: забруднений seed «ідеально» оптимізує в хибне | `make seed-bad` / `make fix-seed` |

## Recording runbook

1. `make setup` перед кожним записом (чистий sandbox, ті самі числа).
2. Для живого #2: `gh auth status` і `ANTHROPIC_API_KEY` у оточенні; PR лишається draft.
3. `outer`/`pr` таргети лише друкують runbook - вони НЕ запускають `claude`.
4. Скинути глобальний конфіг ($HOME, MCP, плагіни), якщо запис їх зачіпає.
5. `make clean` після запису.
